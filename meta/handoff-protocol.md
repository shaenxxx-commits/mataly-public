# meta/handoff-protocol.md

Протокол передачі контексту між сесіями й агентами в MATALY. Застосовується разом із `meta/handoff-current.md` (поточний знімок) і `meta/agent-rules.md`.

Адаптовано з KARCAS-DDA `meta/handoff-protocol.md` (v0.3) за `D-20261019-04`.

## 1. Призначення

Протокол визначає, як передається контекст від одного агента (або сесії) до іншого так, щоб новий агент міг продовжити роботу без реконструкції по пам'яті й без втрати підстави.

Handoff — транспортний формат і набір обов'язкових перевірок, не заміна першоджерелам.

## 2. Ієрархія джерел істини

Будь-яке твердження про зовнішній артефакт вимагає джерела. Пріоритет — від вищого до нижчого:

1. Поточний ввід оператора.
2. Свіжий термінальний вивід (`git status`, `git log`, вміст файлів) у поточній сесії.
3. Вміст репозиторію за конкретним SHA.
4. Документація проєкту (`INVARIANTS.md`, `CURRENT_STATE.md`, `DECISIONS.md`, `meta/`).
5. Handoff / зведення попередніх чатів.
6. Пам'ять ведучого / реконструкція.

Рівень 6 не використовується для тверджень про факти. При конфлікті береться вищий рівень.

### Web-інтерфейс GitHub не є джерелом стану

Веб-сторінка GitHub може віддавати кешоване або застаріле уявлення: старий список файлів, кількість комітів, неактуальний текст. Це не джерело.

Доказ стану віддаленого репозиторію — лише свіжий термінальний вивід:

    git ls-remote origin refs/heads/main     # звіряється з локальним HEAD
    git log -1 --oneline                     # локальний HEAD
    git status --short                       # чисте робоче дерево

Збіг хешів локального HEAD і origin/main — єдине надійне підтвердження, що push досяг віддаленого репозиторію.

Формат факту:

    [ФАКТ] HEAD = <sha>
    [ДЖЕРЕЛО] вивід оператора, <дата>

## 3. Свіжість

«Свіжий» — отриманий у поточній сесії, а не просто згаданий або скопійований із попереднього handoff.

Твердження з попереднього handoff не встановлює поточний стан. Новий агент зобов'язаний запросити актуальні дані, якщо поточне значення значиме.

## 4. Конфлікт джерел

При конфлікті двох джерел агент не згладжує їх мовчки. Зобов'язаний:

1. зафіксувати конфлікт;
2. назвати джерела;
3. віддати перевагу свіжому авторитетному;
4. залишок, що залишився невирішеним, позначати `[НЕВІДОМО]` до розв'язання.

## 5. Маркування тверджень

Кожне твердження про минуле, стан репозиторію або вміст чужих текстів — із явною поміткою:

- `[ФАКТ]` — підтверджено джерелом, джерело названо (відповідає VERIFIED).
- `[ПІДТВЕРДЖЕНО]` — SUPPORTED, перевірка неповна.
- `[ГІПОТЕЗА]` — припущення, джерело не підтверджує.
- `[НЕВІДОМО]` — даних немає.
- `[МОЯ ПОЗИЦІЯ]` — операційна або аналітична позиція агента з поточного питання, не факт.
- `[ЗОВНІШНІЙ — <ім'я>]` — дослівний вивід зовнішнього спостерігача, надісланий у поточному чаті.

`[МОЯ ПОЗИЦІЯ]` ніколи не використовується для маскування зовнішньої думки. Дослівний текст спостерігача не відновлюється по пам'яті.

## 6. Процедура старту нового ведучого

Новий агент не приймає handoff на віру. Обов'язкова послідовність:

**Крок 1 — Верифікація ідентичності handoff.**
Звірити: проєкт, репозиторій, HEAD, активний експеримент/задачу. Що не сходиться — зафіксувати як `[НЕВІДОМО]`.

**Крок 2 — Верифікація поточного стану.**
Запросити свіжі дані (`git log`, `git status`, вміст ключових файлів). Не покладатися на минулі підтвердження.

**Крок 3 — Зафіксувати прогалини.**
Що не вдалося перевірити — явно перелічити. Не заповнювати припущеннями.

**Крок 4 — Встановити повноваження.**
Перевірити, що роль агента визначена: що йому дозволено, що заборонено, хто затверджувач.

**Крок 5 — Лише після цього діяти.**
До завершення кроків 1–4 залежні дії не виконуються.

## 7. Шаблон handoff (транспортний формат)

    HANDOFF PROTOCOL: v0.1-mataly
    PROJECT: MATALY
    REPOSITORY: shaenxxx-commits/mataly
    CURRENT HEAD: <verified SHA / [НЕВІДОМО]>
    ACTIVE EXPERIMENT: <experiment / [НЕВІДОМО]>
    STATUS: <status>
    LAST OPERATOR DECISION: <decision / [НЕВІДОМО]>
    MANDATORY FILES: <list>
    UNVERIFIED: <list>
    OPEN QUESTIONS: <list>
    LAST RESPONSE NUMBER: <n>

Шаблон — транспортний формат, не заміна перевірці за першоджерелами.

## 8. Відновлення втраченого сирого матеріалу

Якщо сирий матеріал не було захоплено в момент події:

- допустимо повторно запросити в джерела й зберегти як `archived-external`;
- архівний запис фіксує: вузол, чат, номер повідомлення, дату повторної видачі;
- якщо джерело не зберегло дослівної відповіді — запис фіксує `UNKNOWN`;
- реконструкція з пам'яті або за резюме неприпустима.

## 9. Anti-patterns (передача контексту)

- вигадування відсутнього стану проєкту;
- твердження, що файл прочитано, коли він не читався;
- звернення зі старим handoff як із поточним станом;
- видача власного аналізу за вивід зовнішнього спостерігача;
- мовчазне вирішення конфлікту джерел;
- старт залежної операції при неперевіреному стані;
- «роби як раніше» без явно визначеної операції;
- реконструкція втраченого сирого матеріалу по пам'яті;
- прийняття web-сторінки GitHub за доказ стану віддаленого репозиторію.

Повний перелік failure cases KARCAS-DDA — зовнішнє джерело: `shaenxxx-commits/karcas-dda`, `meta/handoff-protocol.md` §9–10. За потреби підключаються посиланням, не копіюванням (I14).
